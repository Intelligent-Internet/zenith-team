Zenith Team is a Go server plus a pnpm frontend workspace. For a product-facing walkthrough of using Zenith Team, see the [Quickstart](/quickstart) — this page is about working on the code. The engineering rulebook is `AGENTS.md` in the repository root (with `server/CODEMAP.md` for the server); this page orients and links, it does not restate the rules.

## Requirements

- **Go** 1.26
- **Node.js** 22 or newer
- **pnpm** 9 — `corepack enable` picks the pinned `9.14.2`
- **Docker** for the bundled PostgreSQL, Redis, and Silo stack and for the integration tests

Treat `server/go.mod`, `frontend/package.json`, and the CI workflows as the source of truth for versions.

## First start

Each long-running process gets its own terminal.

1. Install the client workspace once — `frontend/` is its own pnpm workspace, so install inside it, not at the root:

   ```bash
   cd frontend && pnpm install
   ```

2. Start the infrastructure, the server, and the client:

   ```bash
   make infra-up         # PostgreSQL + Redis + Silo (docker/compose.yml)
   make server           # Go API → :8788
   make frontend         # Client app (Vite) → :5173
   ```

3. Open **http://localhost:5173** and check the server:

   ```bash
   curl -s http://127.0.0.1:8788/healthz   # liveness
   curl -s http://127.0.0.1:8788/readyz    # readiness (database reachable at the embedded schema version)
   ```

`make server-local` is the alternative for services you already run natively: copy `server/.env.example` to `server/.env` once and point it at your own PostgreSQL, Redis, and object storage. To actually execute agents you also need a [daemon](/daemon-and-runtimes) and a signed-in provider CLI: `cd server && go run ./cmd/zen auth login`, then `go run ./cmd/zen daemon start`. The full walkthrough is `docs/quickstart.md`; `make help` lists every target.

## Verification

The unit-side lanes a change must pass, all from the repository root:

```bash
make go-unit          # Go: build, vet (both tag lanes), shape + sqlc drift checks, unit tests -race — no Docker
make go-lint          # golangci-lint, pinned repo-locally (make go-fmt formats)
make lint             # Frontend lint        (runs in frontend/)
make typecheck        # Frontend typecheck
make test             # Frontend tests
make build            # Frontend build
make api-lint         # Validate docs/api/spec/openapi.yaml
```

`make gate` runs the full release-quality set — including the tagged Go suites — and is the pre-merge command.

### The API contract loop

`docs/api/spec/openapi.yaml` is the source of truth for the HTTP surface; it `$ref`s one file per domain beside it — edit those, not the index. After changing the spec (or a Go DTO that the spec must mirror), regenerate the committed TypeScript contract:

```bash
make api-generate     # regenerate frontend/src/shared/api/generated/api.generated.ts, then commit it
make api-types-check  # fails when the committed contract is stale
```

### Integration suites

Files named `*_integration_test.go` carry a `//go:build integration` tag, so plain `go test ./...` never compiles them and needs no Docker. The tag adds those files on top of the unit tests; the tagged lane runs on one shared PostgreSQL container owned by `server/tests/testpostgres`, which hands children the database via `BOARDLY_TEST_DATABASE_URL` — a tagged test run without that variable skips. See `server/tests/README.md`.

```bash
make go-integration   # the tagged suites, on the shared container (Docker required)
make go-test GO_TEST_ARGS='./internal/task -run TestName'   # one package or test, same container
```

## Where tests live

Tests are co-located with their package — there is no separate integration tree.

| Change | Test location | Lane |
|---|---|---|
| Server logic | `*_test.go` beside the package | `make go-unit` |
| Server behavior against PostgreSQL, Silo, or Redis | `*_integration_test.go` beside the package | `make go-integration` |
| Frontend | the `frontend/` workspace | `make test` |

Run the check closest to the change first, then expand the scope.

## Before submitting

- Read `AGENTS.md` (and `server/CODEMAP.md` for server work). Where a doc and the code disagree, the code wins — fix the doc in the same change.
- `make gate` passes.
- CI's Go lane gates on `make go-unit`; the integration job is dispatch-only. Run `make go-integration` yourself before merging changes to migrations, sqlc queries, or fixtures.
- If you touched the API surface, `make api-generate` ran and the regenerated contract is committed.
- No credentials, no generated build output, and unrelated local changes left out of the commit.
