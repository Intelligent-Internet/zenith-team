This page is for maintainers with admin access to the GitHub repository. The first part is a one-time checklist. The second part is the regular work.

## One-time setup

### Teams

Create the two teams that [`.github/CODEOWNERS`](https://github.com/Intelligent-Internet/zenith-team/blob/main/.github/CODEOWNERS) names, and give both write access to the repository:

- `@Intelligent-Internet/zenith-team-maintainers`, which owns everything except the paths below
- `@Intelligent-Internet/zenith-team-security`, which owns the security-sensitive paths (sign-in, configuration, middleware, the agent sandbox, provider adapters, migrations, `frontend/electron/`, `.github/`, `.gitleaks.toml` and `SECURITY.md`)

GitHub ignores a CODEOWNERS line whose team does not exist or has no write access.

### Protect `main`

Add a branch ruleset for `main` that:

- requires a pull request before merging,
- requires a review from code owners,
- requires these status checks to pass:
  - `ci-gate`, from the CI workflow. It is the one check that stands for every CI lane.
  - `DCO`, from the DCO app (next step).
- blocks force pushes and deletion.

Do not require the individual CI lanes. They skip when their folders did not change, and `ci-gate` already fails when a lane that ran did not pass.

When you squash-merge, make sure the title is a Conventional Commit: it becomes the commit message on `main`. Contributors check their own commit messages and branch names with the local hooks (`make hooks`).

Keep **secret scanning** and **push protection** on under **Settings → Code security**, together with **Dependabot alerts** and **Dependabot security updates**. They are the project's secret and dependency checks; no workflow repeats them.

### Sign-off

Install the [DCO GitHub App](https://github.com/apps/dco) on the repository. It checks that every commit in a pull request carries a `Signed-off-by` line. [CONTRIBUTING.md](https://github.com/Intelligent-Internet/zenith-team/blob/main/CONTRIBUTING.md#sign-off-every-commit-dco) tells contributors how to add it.

### Security reports and Discussions

- Turn on **Private vulnerability reporting** under **Settings → Code security**. [SECURITY.md](https://github.com/Intelligent-Internet/zenith-team/blob/main/SECURITY.md) and the issue chooser send reporters there.
- Turn on **Discussions** under **Settings → General → Features**. SUPPORT.md, CONTRIBUTING.md and the issue chooser link to it.

### Labels

Create the labels that `.github/release.yml` uses to sort the release notes. The issue templates use some of them too.

| Label | Release notes section |
| --- | --- |
| `breaking` | Breaking changes |
| `enhancement`, `feature` | New features |
| `bug`, `fix` | Fixes |
| `security` | Security |
| `documentation` | Documentation |
| `skip-changelog` | Left out of the notes |

Pull requests with no matching label land under **Other changes**.

### Releases

Only admins can push version tags, because a pushed `v*` tag publishes images and a GitHub Release at once, and runs the release workflow of whatever commit it points at. The `release-tags` ruleset blocks creating, moving and deleting `v*` tags for everyone else; only repository admins and organization admins bypass it, the same as `main-protection`.

Only the desktop jobs use secrets. Leave the repository variable `ALLOW_VULN_BYPASS_FOR_TAG` unset; [Releasing](/developers/releasing) explains the one case for it.

Deployments and desktop builds run in three environments, under **Settings → Environments**. Create them, with their rules, before the cloud side trusts them: GitHub creates a missing environment, with no rules, the first time a job names it.

| Environment | Deployment rule | Holds | Used by |
| --- | --- | --- | --- |
| `dev` | None, so any branch can deploy | The dev variables | `build-deploy.yml` |
| `prod` | The `main` branch and `v*` tags only | The prod desktop variables | `release.yml`'s desktop jobs |
| `desktop-signing` | The `main` branch and `v*` tags only | The six Apple secrets, nothing else | The macOS builds of both |

Only `desktop-signing` holds secrets, so no branch can reach the Developer ID: only code on `main`, which needs a reviewed pull request, or a `v*` tag. A tag can point at any commit, and the release runs that commit's workflow, so whoever may push `v*` tags can reach the Developer ID and the prod downloads without review. That is why the `release-tags` ruleset admits admins only; required reviewers on `desktop-signing` would be the next step. Required reviewers on `prod` are optional: the `main` and tag rulesets already decide what can release, and with reviewers every release waits for approval twice, when its desktop build starts and again before the upload.

To publish the desktop app with releases:

1. Create the three environments as above.
2. Add the six Apple secrets to `desktop-signing`: `ZENITH_TEAM_DESKTOP_MAC_CERTIFICATE_BASE64`, `ZENITH_TEAM_DESKTOP_MAC_CERTIFICATE_PASSWORD`, `ZENITH_TEAM_DESKTOP_MAC_SIGN_IDENTITY`, `ZENITH_TEAM_DESKTOP_MAC_NOTARY_API_KEY_BASE64`, `ZENITH_TEAM_DESKTOP_MAC_NOTARY_API_KEY_ID` and `ZENITH_TEAM_DESKTOP_MAC_NOTARY_API_ISSUER`.
3. Set the `dev` and `prod` variables, and the repository variable `GCP_WORKLOAD_IDENTITY_PROVIDER`, as [Releasing](/developers/releasing#desktop-app) lists. Then set `ZENITH_TEAM_DESKTOP_RELEASE` to `true`.

The desktop jobs then also require `frontend/package.json` to carry each tag's version.

### Actions

- Under **Settings → Actions → General**, keep the default workflow token read-only. Each workflow asks for the extra permissions it needs.
- Require approval before workflows run for first-time contributors from forks.

## Regular work

- **Triage.** Label new issues, and answer or close questions that belong in Discussions.
- **Dependabot.** Each week Dependabot opens grouped update pull requests for Go, npm, Python, GitHub Actions and Docker base images. Merge them once CI is green.
- **Nightly.** The Nightly workflow runs the PostgreSQL integration suites and the Windows and macOS checks each night. A red nightly run means something drifted that no single pull request touched. Fix it before the next release.
- **Security alerts.** Review secret-scanning and Dependabot alerts under the **Security** tab. Close a test fixture as "used in tests"; rotate anything real.
- **Platform bundles.** Workflow and skill content is pinned from a separate plugins repository ([ADR 0016](https://github.com/Intelligent-Internet/zenith-team/blob/main/docs/adr/0016-platform-content-bundles.md)). Updating a pin needs access to that repository, so only maintainers can do it, with `make bundle-bump`, `make bundle-verify` and `make bundle-diff`.
- **Releases.** Cut them as described in [Releasing](/developers/releasing).
