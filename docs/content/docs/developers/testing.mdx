Run every command on this page from the repository root. `make help` lists all targets. Setup is in [Contributing](/developers/contributing).

## Go server

| Target | What it runs | Needs Docker |
| --- | --- | --- |
| `make go-unit` | The shape checks, the sqlc drift check, `go build`, `go vet` (with and without the `integration` tag) and `go test -race` on every package. Integration files are not compiled in. | No |
| `make go-unit-checks`, `make go-unit-tests` | The two halves of `go-unit`, as CI's `server-lint` and `server-test` run them: everything but the tests, then the `-race` tests. | No |
| `make go-integration` | The tagged suites, plus the unit tests again, with `-race`, on one shared PostgreSQL container. | Yes |
| `make go-test` | Like `go-integration`, without `-race`, for the packages and flags in `GO_TEST_ARGS`. | Yes |
| `make go-gate` | `go build`, `go vet` and the complete tagged suite with `-race`, plus the shape and sqlc checks. | Yes |
| `make go-lint` | `golangci-lint` at the pinned version, installed into `.tools/bin` on first use. `make go-lint-fix` applies fixes. `GO_LINT_ARGS` adds flags. | No |
| `make go-fmt` | Formats all Go code. `make go-fmt-check` only reports, and fails when a file needs formatting. | No |
| `make go-sqlc` | Regenerates `server/pkg/db/generated` with the pinned sqlc, installed into `.tools/bin`. Run it after you change a migration or a query. | No |
| `make go-vuln` | Scans the Go dependencies for known vulnerabilities with `govulncheck`. The release workflow runs it fail-closed. | No |

What the extra checks in `go-unit` do:

- **Shape checks** (`make go-shape`) guard a few repository rules a linter cannot express. For example, PostgreSQL test containers may only be started from `server/tests/testpostgres`, and the `zen` CLI must never link the Workflow bundle.
- **sqlc drift check** (`make go-sqlc-check`) regenerates the database code into a temporary folder with the pinned sqlc and fails when the committed code is stale. It never skips: it installs the pinned sqlc into `.tools/bin` when it is missing.
- **Build assets.** Both the shape checks and the integration targets first run `make tools-prepare`, which downloads checksum-pinned npm packages into git-ignored build assets. The first run needs the network; later runs reuse the cache.

### Unit and integration suites

Unit tests sit beside the code they test and need nothing but Go.

Tests that need PostgreSQL, Redis or object storage live in `*_integration_test.go` files that start with `//go:build integration`. A plain `go test ./...` does not compile them. Adding `-tags=integration` adds them on top of the unit tests, so the tagged run is a superset.

For the tagged suites, Docker must be running:

- `server/tests/testpostgres` starts one PostgreSQL container for the whole run and removes it at the end. Each test gets its own database on it.
- A few suites start their own Redis container.
- The S3 storage suite runs only when you point it at a bucket with `ZENITH_TEAM_TEST_S3_ENDPOINT`, `ZENITH_TEAM_TEST_S3_BUCKET`, `ZENITH_TEAM_TEST_S3_ACCESS_KEY_ID` and `ZENITH_TEAM_TEST_S3_SECRET_ACCESS_KEY`. Otherwise it skips.

A tagged test run without the shared database skips instead of failing. In CI, or with `TEST_REQUIRE_DOCKER=1`, a missing database is a failure.

The Makefile sets `GOFLAGS=-p=2`, so at most two packages hit the shared database at once.

### Run one test

A unit test, with no Docker:

```bash
cd server && go test ./internal/task -run TestName
```

A test that needs PostgreSQL, through the shared container:

```bash
make go-test GO_TEST_ARGS='./internal/task -run TestName'
```

Run `make go-integration` before you open a pull request that changes migrations, sqlc queries or test fixtures. CI does not run these suites on pull requests; it runs them every night.

## Frontend

All of these run inside `frontend/`, its own pnpm workspace. Run `cd frontend && pnpm install` once first.

| Target | What it runs |
| --- | --- |
| `make lint` | The import-cycle and layer check, then the Prettier format check (`pnpm lint`). |
| `make typecheck` | TypeScript type check of the app. |
| `make build` | Type check, then the production Vite build. |
| `pnpm --dir frontend electron:security:scan` | Static checks of the Electron hardening rules: fuses, CSP, IPC exposure, permissions and `webPreferences`. |

The project adds no other frontend tests. Check UI changes in the running app, and add screenshots to the pull request.

## API contract

The HTTP contract lives in `docs/api/spec/`, with `openapi.yaml` as the index.

| Target | What it runs |
| --- | --- |
| `make api-lint` | Validates the spec: schemas, `$ref` links and operation IDs. |
| `make api-types-check` | Regenerates the TypeScript API types into a temporary file and fails when the committed file is stale. |
| `make api-generate` | Regenerates `frontend/src/shared/api/generated/api.generated.ts`. Run it after you change the spec, and commit the result. |

A Go unit test, `TestOpenAPISpecMatchesRouteTable`, also fails `make go-unit` when the spec and the server's routes disagree.

## Voice worker

`make voice-gate` runs the voice worker's lint, format check and tests in `voice-agent/`. It needs `uv`.

## Everything at once

`make gate` runs `api-lint`, `api-types-check`, `voice-gate`, `go-gate`, `lint`, `typecheck` and `build`. It needs Docker and `uv`.

## CI

`.github/workflows/ci.yml` runs on every pull request, on every push to `main`, and by hand.

### Which lanes run

A first job, `changes`, looks at the changed files and picks the lanes. Each lane lists every file its checks read, including shared files outside its folder, so a change to one of those alone still runs the lane:

| Lane | Runs when these change | What it runs |
| --- | --- | --- |
| `server-test` | `server/**`, `docs/api/**`, `deploy/production.env.example`, `deploy/docker-compose.production.yml` | `make go-unit-tests`: the unit tests with `-race`, as many packages at once as the runner has cores |
| `server-lint` | The same as `server-test` | `make go-fmt-check`; `make go-unit-checks` (the rest of `go-unit`: the shape checks, the pinned sqlc drift check, `go build` and both `go vet` runs); `make go-lint` (on a pull request, only findings new since its merge base fail); and cross-builds of `zen` and `zenith-team-mcp` for macOS, and `zenith-team-mcp` for Windows |
| `frontend` | `frontend/**`, `docs/api/spec/**`, `LICENSE`, `THIRD_PARTY_NOTICES.md` | `make lint typecheck`, `make api-lint api-types-check`, the production build (`make build`) and the Electron security scan |
| `voice` | `voice-agent/**` | `ruff check`, `ruff format --check`, the Python tests, and a Docker build |
| `selfhost` | `deploy/**`, a Dockerfile, `LICENSE`, `THIRD_PARTY_NOTICES.md` | Builds both images, runs `make selfhost-env`, boots the Compose stack, and checks that `/readyz` and the web app answer |
| `desktop` | `frontend/electron/**`, `frontend/forge.config.cjs`, `frontend/package.json`, `frontend/pnpm-lock.yaml`, `.github/actions/desktop-setup/**` | Unsigned desktop installers for macOS (arm64) and Linux (x64) with `pnpm electron:make`, kept a week as workflow artifacts |
| `workflows` | `.github/**` | `actionlint` (with `shellcheck`) on the workflows, and `zizmor` (medium severity and above) on the workflows and the composite action |

A change to `.github/workflows/ci.yml` runs every lane. A change to the `Makefile` runs every lane except `desktop` and `workflows`. A push to `main` runs every lane except `desktop`, which still runs only when its files change, so a green `ci-gate` on a `main` commit covers the whole tree; releases rely on that. Each push to `main` gets its own run, so none is skipped. A manual run from the Actions tab runs every lane.

`server-lint` caches the pinned `golangci-lint` and `sqlc` (`.tools`) and golangci-lint's analysis; `server-test` keeps its own `-race` build cache; and the `desktop` lane caches the pnpm store and Go builds. Nothing that is signed or published restores a cache.

### The required check

**`ci-gate`** is the one required check. It fails when any lane failed or was cancelled; a lane that did not need to run is skipped.

Pull requests from forks run with a read-only token and no secrets.

### Nightly

`.github/workflows/nightly.yml` runs every night and by hand:

| Job | What it runs |
| --- | --- |
| `integration` | `make go-integration`: every PostgreSQL suite with `-race` |
| `vulnerabilities` | `make go-vuln`, the scan a release runs, so a new advisory shows up before a tag |
| `windows` | On Windows: the platform-content tests, a few `zenith-team-mcp` tests, and a build of `zenith-team-mcp`, proving the pinned content survives a CRLF checkout |
| `macos` | On macOS: the daemon's sandbox tests, which keep agents away from sign-in files and other runs' folders |

### Secrets and dependencies

GitHub does this work, so no workflow repeats it: secret scanning with push protection refuses a push that contains a known secret format, and Dependabot alerts and security updates track vulnerable dependencies. Dependabot also checks Go modules, npm packages, Python packages, GitHub Actions and Docker base images every week, skipping versions younger than a week. The nightly run and every tag release run `govulncheck`, and a release fails on a known vulnerability (see [Releasing](/developers/releasing)).

`.github/workflows/codeql.yml` runs CodeQL code scanning on the Go server, the TypeScript apps, the voice worker and the workflows: on every pull request, on pushes to `main` and weekly. Findings appear under **Security → Code scanning** and on the pull request; it is not a required check.

## Local git hooks

Run `make hooks` once per clone. It points git at `.githooks/`, whose hooks share one set of rules in `.githooks/conventions.sh`:

| Hook | Checks |
| --- | --- |
| `pre-commit` | Refuses commits on `main` and on a branch whose name breaks the rules below. Scans the staged changes for secrets with `gitleaks` and `.gitleaks.toml`, when [gitleaks](https://github.com/gitleaks/gitleaks) is installed. |
| `commit-msg` | The subject is a Conventional Commit, such as `fix(daemon): retry the first claim`. |
| `pre-push` | Every pushed branch name, and the subject of every new commit on it, so a commit made with `--no-verify` is still caught. Tags and branch deletions pass. |

The rules follow the community conventions:

- **Commit subjects** are `type(scope)!: description` ([Conventional Commits](https://www.conventionalcommits.org/)). Types are the standard list: `build`, `chore`, `ci`, `docs`, `feat`, `fix`, `perf`, `refactor`, `revert`, `style`, `test`. Type and scope are lowercase, `!` marks a breaking change, there is no trailing period, and the subject is at most 72 characters. Merge, revert, `fixup!` and `squash!` subjects pass.
- **Branch names** are `type/short-name` with the same types (plus `hotfix` and `release`), in lowercase words joined by hyphens: `feat/task-reorder`, `fix/daemon-first-claim`, `release/1.4.0`. Dependabot's `dependabot/…` branches pass.

Pull request titles follow the same Conventional Commit form, because they become the squash-merge commit message.
