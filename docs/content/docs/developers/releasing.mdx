A release starts with one action: a maintainer pushes a version tag on `main`. `.github/workflows/release.yml` does the rest. Only its desktop job uses secrets, the Apple signing credentials in the `desktop-prod` environment; everything else runs on the workflow's own GitHub token.

Only a tag publishes a release. Merges to `main` that change the server, and manual runs of `.github/workflows/image.yml` at a branch or tag, publish one server image tagged `sha-<full commit>` and nothing else: a build of that commit, not a release. A release cut at the same commit rebuilds the image and repoints `sha-<full commit>`, so deployments pin the digest too: `sha-<full commit>@sha256:<digest>`.

## Before you tag

- The commit you tag is on `main`, and CI is green on it.
- The integration suites pass. The nightly CI run includes them; check the latest one, or start the CI workflow by hand. See [Testing](/developers/testing#ci).
- `make go-vuln` finds no known vulnerabilities in the Go dependencies. The release stops on any (see below).
- Merged pull requests carry the right labels, so the release notes sort them (see below).
- Docs and `deploy/production.env.example` cover any new setting.
- When desktop releases are on, `frontend/package.json` has the tag's version. The desktop job stops otherwise.

## Cut the release

```bash
git checkout main
git pull
git tag -a v1.3.0 -m "Zenith Team v1.3.0"
git push origin v1.3.0
```

Two kinds of tag start the workflow:

| Tag | Kind | Moves `latest`? |
| --- | --- | --- |
| `v1.3.0` | A release | Yes |
| `v1.3.0-rc.1`, `v1.3.0-beta.2`, `v1.3.0-alpha.1` | A pre-release, for testing | No |

A pre-release never moves the `latest` image tag or the latest GitHub Release, so people who follow `latest` do not get it. Any other tag shape that starts with `v` and a version fails in the first step.

<Callout type="warning">
A pushed tag publishes images and a GitHub Release right away. Check the commit before you push the tag.
</Callout>

## What the workflow does

Verify runs first; images, binaries and the desktop app then build side by side, and publish runs last. One release runs at a time per tag, and a running release is never cancelled.

### 1. Verify

- Checks the tag shape and decides whether it is a pre-release.
- Checks that the tagged commit is on `main`. A tag anywhere else fails here.
- Scans the Go dependencies for known vulnerabilities with `make go-vuln`. This is fail-closed: any finding stops the release.
- Runs `make go-fmt-check`, `make go-unit`, and the frontend checks `make lint typecheck api-lint api-types-check`.

**Releasing despite a vulnerability.** Sometimes a finding has no fix yet and does not affect Zenith Team. A maintainer can then release one tag anyway: set the repository variable `ALLOW_VULN_BYPASS_FOR_TAG` to exactly that tag, such as `v1.3.1`, and re-run the workflow. The bypass works only for that one tag, and the run shows a warning. Remove the variable afterwards, and say in the release notes why the bypass was needed.

### 2. Images

Builds the server and web images (`server/Dockerfile` and `frontend/Dockerfile`) for `linux/amd64` and `linux/arm64`, each on a native runner, and pushes them to GitHub Container Registry. `.github/workflows/build-image.yml` does the work, the same steps `image.yml` uses: the build jobs hold no registry credentials, and one publish job pushes the platform images, merges them and tags the result.

- `ghcr.io/intelligent-internet/zenith-team-server`
- `ghcr.io/intelligent-internet/zenith-team-web`

For `v1.3.0`, each image gets four tags:

| Tag | Meaning |
| --- | --- |
| `1.3.0` | This exact release. Self-hosters should pin this. |
| `1.3` | The newest patch of the 1.3 line. |
| `latest` | The newest release. |
| `sha-<full commit>` | The tagged commit. Unreleased commits get this tag too, from `image.yml`. |

A pre-release such as `v1.3.0-rc.1` gets only its exact tag, `1.3.0-rc.1`, plus `sha-<full commit>`.

Each image also carries an SBOM (its list of components) and build provenance (a record of how it was built), plus a GitHub build attestation that ties its digest to this repository, the ref and commit it was built from, and the workflow. Check one with:

```bash
gh attestation verify oci://ghcr.io/intelligent-internet/zenith-team-server:1.3.0 \
  --repo Intelligent-Internet/zenith-team \
  --signer-workflow Intelligent-Internet/zenith-team/.github/workflows/build-image.yml \
  --source-ref refs/tags/v1.3.0 \
  --deny-self-hosted-runners
```

Always pin `--source-ref`: without it, a build of any branch passes. For a `sha-<commit>` image from `main`, use `--source-ref refs/heads/main --source-digest <commit>`.

The first publish creates each GHCR package as private. A maintainer makes `zenith-team-server` and `zenith-team-web` public once, in the package settings; until then nobody can pull them anonymously.

### 3. Binaries

Builds `zen` and `zenith-team-mcp` for each system and packs them into one archive per system:

| System | `zen` | `zenith-team-mcp` |
| --- | --- | --- |
| Linux `amd64`, `arm64` | Yes | Yes |
| macOS `amd64`, `arm64` | Yes | Yes |
| Windows `amd64` | Not yet | Yes (`.exe`) |

Archives are named like `zenith-team_v1.3.0_linux_amd64.tar.gz`. Each one also holds `LICENSE` and `THIRD_PARTY_NOTICES.md`. `zen version` reports the release version. A `checksums.txt` file lists the SHA-256 of every archive.

### 4. Publish

Creates a GitHub Release named `Zenith Team v1.3.0` with the archives and `checksums.txt` attached, plus the desktop files when the desktop job ran (see [Desktop app](#desktop-app)), marked as a pre-release when the tag is one. Every attached file gets a build attestation; check one with `gh attestation verify <file> --repo Intelligent-Internet/zenith-team --signer-workflow Intelligent-Internet/zenith-team/.github/workflows/release.yml --source-ref refs/tags/v1.3.0`. The release notes are generated from the pull requests merged since the last release.

## Release notes

`.github/release.yml` sorts the merged pull requests by label:

| Section | Labels |
| --- | --- |
| Breaking changes | `breaking` |
| New features | `enhancement`, `feature` |
| Fixes | `bug`, `fix` |
| Security | `security` |
| Documentation | `documentation` |
| Other changes | everything else |

Pull requests labelled `skip-changelog`, and those opened by Dependabot, are left out. You can edit the notes on GitHub after the release is published.

## Desktop app

Desktop builds come in two apps, each built for one server, chosen by what starts the build:

| | Zenith Team | Zenith Team Dev |
| --- | --- | --- |
| Started by | A `v*` release tag, always | A manual run of **Desktop Dev** (`.github/workflows/desktop-dev.yml`) from `main` |
| Environment | `desktop-prod` | `desktop-dev` |
| Version | The tag's | The `X.Y.Z` of `frontend/package.json` plus `-dev.<run number>` |
| Published as | Files on the tag's GitHub Release | A pre-release `desktop-dev-v<version>`, never marked latest |

The two apps install side by side with separate data, and each updates only from its own channel.

The release builds Zenith Team while the repository variable `ZENITH_TEAM_DESKTOP_RELEASE` is `true`; otherwise its desktop job is skipped and the rest of the release runs as before. A reviewer approves each build in the `desktop-prod` environment. Both apps build:

- signed and notarized macOS installers, a `.dmg` to download and a `.zip` for updates, for `arm64` and `x64`;
- an unsigned Linux `.zip` for `x64`. Windows joins once `zen` builds there.

Each build signs in to its environment's `DESKTOP_API_ORIGIN` and checks for updates at its `DESKTOP_RELEASE_BASE_URL`; self-hosters still build their own (see [Desktop app](/desktop-app)). Every file is attached with a build attestation, plus:

| File | What it is |
| --- | --- |
| `latest.json` | The download manifest the website reads, and the app's update manifest |
| `update-darwin-<arch>.json` | The macOS update feed |
| `release-publish.json` | Where a static host puts each file: installers under `<version>/`, the manifests at fixed paths, and the channel (`prod` or `dev`) |

A Zenith Team pre-release carries its installers but no manifests, so it moves nothing; every Zenith Team Dev build moves the dev manifests. Copying the files to `DESKTOP_RELEASE_BASE_URL`, where the website and the app look for them, happens outside this repository, so it holds no cloud credentials. Check each file's attestation first: against `release.yml` and the tag for Zenith Team, against `desktop-dev.yml` and `refs/heads/main` for Zenith Team Dev. The installers can always be downloaded from their GitHub Release.

Settings:

| Where | Name | Holds |
| --- | --- | --- |
| Repository variable | `ZENITH_TEAM_DESKTOP_RELEASE` | `true` to build Zenith Team with each release |
| `desktop-prod` and `desktop-dev` variable | `DESKTOP_API_ORIGIN` | The server the app signs in to, such as `https://api.example.com` |
| `desktop-prod` and `desktop-dev` variable | `DESKTOP_RELEASE_BASE_URL` | Where its installers and manifests are served, such as `https://downloads.example.com/zenith-team` |
| `desktop-prod` and `desktop-dev` secret | `ZENITH_TEAM_DESKTOP_MAC_CERTIFICATE_BASE64`, `..._MAC_CERTIFICATE_PASSWORD` | The Developer ID Application certificate (.p12) and its password |
| `desktop-prod` and `desktop-dev` secret | `ZENITH_TEAM_DESKTOP_MAC_SIGN_IDENTITY` | The signing identity name |
| `desktop-prod` and `desktop-dev` secret | `ZENITH_TEAM_DESKTOP_MAC_NOTARY_API_KEY_BASE64`, `..._NOTARY_API_KEY_ID`, `..._NOTARY_API_ISSUER` | The App Store Connect API key used to notarize |

Packaging is checked before a tag by CI's `desktop` lane, which builds unsigned macOS (arm64) and Linux (x64) installers with the same setup (`.github/actions/desktop-setup`) whenever a pull request changes the desktop packaging, and keeps them as workflow artifacts for a week. Start the CI workflow by hand to run it on demand.

## If a release fails

- **Verify failed.** Fix the problem on `main`, then tag a new patch version. Do not move an existing tag. For a vulnerability finding, see the bypass above.
- **A later job failed.** Re-run the failed jobs from the workflow run page. If the code itself must change, tag a new patch version.
