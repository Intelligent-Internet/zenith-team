Zenith Team keeps two kinds of data:

- **PostgreSQL** holds everything structured: companies, agents, tasks, conversations and run history.
- **S3-compatible object storage** holds the bytes of uploaded files, such as chat attachments.

Redis carries realtime updates and the queue that starts Schedules on time. PostgreSQL stays the source of truth for all of it, so Redis needs no backup.

## The bundled storage service

The Compose stack runs its own S3-compatible storage service, named `storage`, with these settings:

| Setting | Value |
| --- | --- |
| Endpoint | `http://storage:9000`, inside the Docker network only |
| Bucket | `zenith-team-attachments`, created by the one-off `storage-init` service at start |
| Access key | `zenith-team` |
| Secret key | `STORAGE_S3_SECRET_ACCESS_KEY`, generated by `make selfhost-env` |
| Data | the `storage-data` Docker volume |

The service publishes no port. That is fine, because uploads and downloads pass through the Zenith Team server: browsers and the desktop app never talk to storage directly. A single file can be up to 100 MB.

An upload that is finished but never attached to anything is cleaned up after a day. `ATTACHMENT_ABANDONED_READY_GRACE_SECONDS` changes that delay.

## Share links

One feature hands out a link that points straight at storage: posting an image to **Facebook** or **Instagram** from a [personal social account](/self-hosting/environment-variables#personal-social-accounts). The link lasts one hour, and Meta's servers fetch the image from it.

For that, storage must be reachable from the internet over HTTPS. The bundled service is not, and the server refuses to share a link that does not start with `https://`. If you need this feature, use an S3 service with a public HTTPS endpoint, as below. Everything else works with the bundled service.

## Use your own S3 service

Any S3-compatible service works: AWS S3 or another provider. Every server copy must use the same store.

1. **Create the bucket yourself.** The stack only creates buckets on the bundled service.
2. **Create a key pair** that can read, write and delete objects in that bucket.
3. **Set the values** in `deploy/.env`:

   ```dotenv
   STORAGE_S3_ENDPOINT=https://s3.us-east-1.amazonaws.com
   STORAGE_S3_REGION=us-east-1
   STORAGE_S3_BUCKET=my-zenith-team-files
   STORAGE_S3_ACCESS_KEY_ID=<access key ID>
   STORAGE_S3_SECRET_ACCESS_KEY=<secret access key>
   STORAGE_S3_USE_PATH_STYLE=false
   ```

   Set `STORAGE_S3_ENDPOINT` even for AWS: when it is empty, the Compose stack falls back to the bundled service. `STORAGE_S3_USE_PATH_STYLE` defaults to `true`. Many self-run S3 services need `true`; AWS S3 works with `false`. Set `STORAGE_S3_SESSION_TOKEN` only for temporary credentials.

4. **Remove the bundled service.** In `deploy/docker-compose.production.yml`, delete the `storage` and `storage-init` services and the server's `depends_on` entry for `storage-init`. Otherwise the unused service keeps running, with your real secret key as its password.

5. Run `make selfhost-up`.

### Move existing files

Switching storage does not copy anything. If people have already uploaded files:

1. Stop the server, so no new files arrive.
2. Copy every object from the old bucket to the new one with an S3 copy tool, and check the copy.
3. Change the settings, then start the server again.

Keep the old bucket until you have checked that old attachments still open.

## Back up and restore

Back up PostgreSQL first, then the files. A file saved after the database dump does no harm on restore. The other way round, the database would point at files that are missing.

### Back up

Run these from the repository root.

```bash
# 1. The database
docker compose -f deploy/docker-compose.production.yml exec postgres \
  pg_dump -U zenith_team -d zenith_team --format=custom --file=/tmp/zenith-team.dump
docker compose -f deploy/docker-compose.production.yml cp \
  postgres:/tmp/zenith-team.dump ./zenith-team-$(date +%F).dump

# 2. The bundled file storage
docker run --rm \
  -v zenith-team-production_storage-data:/data:ro \
  -v "$PWD":/backup \
  alpine tar czf /backup/zenith-team-storage-$(date +%F).tar.gz -C /data .
```

Docker names the volumes after the Compose project, `zenith-team-production`. `docker volume ls` shows them.

For your own S3 service, turn on bucket versioning, or copy the bucket on a schedule with an S3 sync tool. For your own PostgreSQL, use its snapshot tooling.

Store backups away from the server, and test a restore now and then. Also keep a safe copy of `deploy/.env`. A server restored with different secrets signs everyone out, and loses what those secrets protect, such as connected social accounts.

### Restore

Restore into the same release you backed up from, with the server stopped:

```bash
docker compose -f deploy/docker-compose.production.yml stop server web

# The database
docker compose -f deploy/docker-compose.production.yml cp \
  ./zenith-team-2026-10-12.dump postgres:/tmp/restore.dump
docker compose -f deploy/docker-compose.production.yml exec postgres \
  pg_restore --clean --if-exists -U zenith_team -d zenith_team /tmp/restore.dump

# The bundled file storage
docker compose -f deploy/docker-compose.production.yml stop storage
docker run --rm \
  -v zenith-team-production_storage-data:/data \
  -v "$PWD":/backup \
  alpine sh -c 'rm -rf /data/* /data/.[!.]* && tar xzf /backup/zenith-team-storage-2026-10-12.tar.gz -C /data'

docker compose -f deploy/docker-compose.production.yml up -d --wait
```

<Callout type="warning">
A restore throws away everything written after the backup was taken, such as new messages and runs. People who signed in after the backup may need to sign in again, on their computers too.
</Callout>
