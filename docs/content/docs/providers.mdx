title: Providers
description: The two provider CLIs that execute runs — Codex and Claude Code — and how each handles sessions, skills, connectors, models, and usage.
---

A provider is the vendor CLI that actually executes a [run](/runs) on your computer: exactly `codex` (Codex) or `claude` (Claude Code). The set is closed — a provider name is validated against it everywhere, and nothing else can execute. Each [agent's](/agents) provider is derived from its [runtime](/daemon-and-runtimes) binding, never chosen separately: bind the agent to a Codex runtime and it runs on Codex.

## Supported tools

| | `claude` (Claude Code) | `codex` (Codex) |
|---|---|---|
| **Launch** | One `claude` process per turn, in stream-JSON mode | A `codex app-server` process speaking JSON-RPC |
| **Session resumption** | `--resume` with the stored session id | `thread/resume` against the app-server |
| **Skills** | Written into the workspace under `.claude/skills` | Written into the per-run `CODEX_HOME/skills` |
| **MCP and connectors** | Daemon-written `--mcp-config` file | `mcp_servers` in the per-run `CODEX_HOME` config |
| **Model and thinking level** | `--model` and `--effort` flags | Model and `model_reasoning_effort` on the thread |
| **Usage basis** | `per_run` | `session_cumulative` |

## Session resumption

Both providers can continue a conversation across turns, keyed to a session pointer Zenith Team stores per run — which is why a task's workspace directory is reused and [must never move](/workspaces#the-company-workspace-tree).

- **Claude Code** is spawned fresh for every turn and resumes by passing `--resume` with the prior session id. If the CLI positively rejects the resume — the transcript it names is gone — the pointer is dropped and the turn retries on a fresh session.
- **Codex** runs as an app-server and resumes a thread over `thread/resume`. If the live resume is rejected, the turn lands on a fresh thread, and the agent is told so with a continuity notice instead of silently starting over.

Failures that poison a session — a context overflow, an unprocessable history — force the next attempt onto a fresh session; see the [failure reference](/runs#failure-reason-reference).

## Skills

The daemon materializes the agent's [skills](/skills) into each provider's native discovery location before the CLI starts: for Claude Code, a `.claude/skills` directory in the run's working directory; for Codex, a `skills/` directory inside the run's private `CODEX_HOME`. For Codex, the run's assigned skills win on a name conflict with skills already installed on the machine. Runtime-local skills an agent has disabled are hidden from the process — through settings deny rules on Claude Code, and `skills.config` disable entries on Codex.

## MCP and connectors

Execution authority comes from the run's frozen [connector contract](/connectors-and-plugins), and each provider receives it natively:

- **Claude Code** gets a daemon-written MCP config file via `--mcp-config`. When the agent carries a managed config, the run also gets `--strict-mcp-config`, so it cannot inherit MCP servers from your personal Claude Code setup.
- **Codex** gets its `mcp_servers` written into the per-run `CODEX_HOME` configuration, and any user-supplied `mcp_servers` overrides are stripped — the frozen contract is the only source.

Connector credentials and native configuration never leave the machine.

## Model and thinking level

An agent's model override and thinking level are frozen into the run at enqueue and handed to the provider natively: Claude Code as `--model` and `--effort` flags, Codex as the model and `model_reasoning_effort` on the thread. An empty thinking level deliberately injects nothing, so the CLI's own default applies. The valid level vocabulary is provider-native — Claude Code's `low | medium | high | xhigh | max`, Codex's `none | minimal | low | medium | high | xhigh` — and the exact choices per model come from [model discovery](#model-discovery) below. Saving an agent checks the level against its runtime's provider: Claude Code takes only its five words, Codex any well-formed catalog level, and anything else is refused.

## Usage basis

The two providers count tokens differently: Claude Code reports each turn's own consumption (`per_run`), while Codex reports running totals for the whole resumed session (`session_cumulative`), so a later turn's numbers supersede — rather than add to — the session's earlier ones. Zenith Team stamps every usage fact with its basis; what is recorded per run lives in [Runs](/runs#usage).

## Sign-in and credentials

You sign in with the vendor's own CLI, on your own machine — `claude` for Claude Code, `codex` for Codex. Zenith Team never holds provider credentials: no API key, token, or login ever enters Zenith Team's cloud, and the daemon launches the CLI under whatever authentication it already has locally. When that authentication is missing or expired, runs on that machine fail with `agent_error.provider_auth_or_access` — the fix is always to re-authenticate the vendor CLI itself, per the [troubleshooting checklist](/daemon-and-runtimes#troubleshooting-an-offline-runtime).

## Model discovery

Anyone who may use a runtime — its registrant, or any member while it is Public — can browse the model catalog of that one exact online runtime — the models that specific installation offers, with each model's thinking-level choices and defaults. Discovery is transient: the request runs against the machine, times out if the daemon does not answer promptly, and the result is never stored — it exists to pick a value, not to build a registry. For a Codex runtime, the daemon asks the installed Codex CLI for its own catalog, so the answer reflects that installation and account. For a Claude Code runtime, the daemon serves a fixed catalog of Claude model aliases. Selected ids are passed back to the provider unchanged as the [agent model override](/agents).
