A conversation is the thread of record for a [task](/tasks), a [schedule](/schedules), or a private direct chat with one [agent](/agents), and the owner of one ordered item sequence. Everything said in it — by you, by the agent, and by the agent's tools — is a row of that sequence, and every row is labelled with the [run](/runs) that consumed or produced it.

The chat you read and the transcript you inspect are not two records. They are two filtered reads of the same rows, so they can never disagree about what was said or in what order.

## Three kinds of conversation

| Kind | What creates it | Who can read it |
|---|---|---|
| `task` | Created with its task — every task owns exactly one conversation | The people who can see the task's project ([project access](/project-access)); posting needs the right to write its tasks. It keeps its project after the task is deleted |
| `direct` | You, by opening a chat with an agent | Only its creator |
| `schedule` | Created with its schedule — the thread its firings append to | Only the schedule's creator |

You can hold several independent direct chats with the same agent. Starting a new chat (a fresh `requestKey`) opens a new conversation and a new provider session without touching your earlier chats; opening a chat without a key reuses your oldest active chat with that agent, or creates one when you have none. A direct chat can carry an optional title of up to 120 characters.

<Callout type="info">
Direct conversations are creator-private even from the company owner. Two members share the same agent but see disjoint chat lists, and another member's direct chat answers as if it did not exist. This protects chat visibility on the server, not local filesystem access: the assigned machine/provider receives the Run input, and direct Runs use the shared Company workspace.
</Callout>

## Messages and the transcript

A conversation holds one immutable, ordered item stream. Each item has a `type`, and the type — never a stored flag — decides which surface shows it:

| Item type | Where it appears | What it is |
|---|---|---|
| `user_message` | Chat | The words you sent |
| `agent_text` | Chat and transcript | Agent text committed when a provider item completes |
| `reasoning` | Transcript | The agent's thinking |
| `tool_call` | Transcript | A tool the agent invoked |
| `tool_result` | Transcript | What that tool returned |
| `error` | Transcript | A provider-reported error |

The chat surface shows `user_message` and `agent_text`. The transcript shows every item the run produced, grouped by the run's id — and the two overlap on `agent_text` deliberately, because the answer is both the chat's message and the run's output, read twice rather than stored twice.

Both surfaces read one shared sequence counter, advanced under a per-conversation lock — every writer takes that lock first, so exactly one writer decides what came next, and the chat and the transcript can never disagree about order. Two consecutive chat messages are usually not consecutive numbers, because the run detail between them took numbers of its own; a gap is not a lost message.

Items are immutable. An item is written once, with its content — there is no placeholder that a later step fills in. Corrections are new items, cancelling or failing a run cannot take back an answer you already read, and a run that said nothing has no answer row: the absence is the record.

Answers arrive as completed provider items, without waiting for the Run to finish. The browser receives those committed items, not individual tokens; Desktop may also show disposable local token preview. Cancelling a Run keeps every already committed item. Reasoning/tool-only items stay in the transcript, and a conversation with only those items has no answer preview in the chat list.

The server's transcript and a provider's native session are separate. Every Run receives the frozen trigger prompt, the Agent/Task brief and a bounded snapshot of the Conversation's recent chat with each message's author, so a fresh provider session still knows what was said and by whom. A resumed session receives only what it missed, and a session that could not be restored is told so. This is not full transcript replay: the agent reads older history on demand.

Every item belongs to a run — the run that consumed your words, or the run that wrote the agent's. A conversation with no agent to answer therefore refuses a message outright: a task assigned to a person, or a direct chat whose agent was deleted, cannot take one.

## Sending while an agent is running

One conversation has at most one active run. A send into an idle conversation starts a fresh run; a send while a run is still open joins a durable queue behind it — up to 20 prompts deep — and waits there even while every machine is offline.

A queued prompt is not yet part of the conversation: nothing is appended to the stream until the active run reaches a terminal state, and the same transaction that ends the run promotes the queue head into a message and its fresh run. A queued prompt has no run either — the run comes into existence only when promotion creates it — so what you follow while waiting is the queue item. While a prompt waits, you can reorder the queue or remove items from it.

A message can also reopen finished-looking work. Sending into a task whose latest outcome is `failed` is the explicit resume: the fresh run returns the task to `in_progress`, on the same conversation history. Tasks that are `done` or `cancelled` refuse new messages.

A queued prompt is re-checked at promotion. If the conversation no longer admits it — the agent is gone, or the task no longer accepts new work — the prompt is removed with a durable removal reason instead of starting a run, and the next item is considered. An automatic retry of a failed run stays ahead of your queued prompts: promotion happens only once the retry chain is terminal.

## Attachments

Files ride a message: you stage an upload first, then reference it by id when you send — see [Attachments](/attachments).

## Pin, archive, and delete

Direct conversations carry creator-scoped filing state — `pinnedAt` and `archivedAt` timestamps, private to you. Task conversations carry none, and there is no per-conversation unread flag on either: what tells you something happened is the [Inbox](/notifications).

| Action | What it does |
|---|---|
| **Pin** | Stamps `pinnedAt`, so pinned chats can be ordered by when you pinned them |
| **Archive** | Removes the chat from your list. It stays readable by id. Archiving does not gate creation — a new chat with the same agent starts a new conversation and a new provider session whether or not older chats are archived; a keyless quick-open only reuses unarchived chats |
| **Delete** | Does not exist. Archiving is how you retire a direct chat |

Conversation history also outlives the work it recorded: deleting a task detaches its conversation rather than deleting it, so the items, runs, and usage evidence remain readable.
