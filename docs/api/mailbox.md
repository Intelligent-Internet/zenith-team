---
title: Mailbox and Agent Mail
summary: Company Email, retained inbound messages, and reviewable Agent drafts
---

The Mailbox domain owns two coupled interfaces: the Company's one inbound
email address, and reviewable outbound Agent Mail drafts sent from that
address. It is separate from Inbox: email is user content, while Inbox items
are Zenith Team notifications.

Every Mailbox and Agent Mail route requires `mailbox.manage`, currently granted
only to Company owners. Under this policy admins and members receive
`403 company_permission_required`, including when acting through an Agent Run.
This covers state and unread counts, message lists and bodies, attachments,
configuration, and draft creation, review
and sending. `GET /companies/{companyId}/mailbox` returns `disabled`,
`unconfigured`, or `active` to an authorized member. Mailbox, message, attachment,
draft-group, draft, and delivery ids are all generated by PostgreSQL.

The role grant lives only in `server/internal/auth/permission.go`. Handlers and
services check `Can(mailbox.manage)`; queries and realtime audiences bind
`RolesWith(mailbox.manage)`; the UI consumes the server-resolved permission set.
Granting an additional Company role this permission therefore applies across
Mailbox and Agent Mail without changing their access checks. An Agent Run uses
its acting member's permission and gains no independent role or access grant.

Inbound message metadata is retained for 30 days. The list is a newest-first
seek page. Message detail and attachment download may contact the email
provider and can return `410 mailbox_message_expired`, `429
mailbox_provider_rate_limited`, or `503 mailbox_provider_unavailable`.

## Agent Mail

An active Run acting for a member with `mailbox.manage` creates one draft group
using that member's ordinary bearer principal plus
the same supplemental headers as other Run-authorized operations:

```
X-Zenith-Team-Run-Token: brt_<64 lowercase hex characters>
Idempotency-Key: <uuid>
```

The resolved token exclusively supplies the Run and Agent identity; neither is
accepted in the body, and the Conversation in the path must belong to that
Run. The body is only `{ "drafts": [...] }`. PostgreSQL generates every group,
draft, and delivery id. First creation returns `201`; an exact replay returns
the existing group with `200`. Reusing the key or Run with different canonical
content returns `409 agent_mail_draft_conflict`.

A member with `mailbox.manage` may edit or delete drafts while they are reviewable,
then queue one draft or a complete version-pinned group. Delivery is durable and asynchronous.
Queueing is the committed authorization point: a later membership revocation
or account deletion does not recall mail already accepted into the send queue.
Daily recipient limits return `429 agent_mail_send_limit_exceeded`.

Mailbox permission does not override Conversation or Project access. A task
chat's drafts also follow its Project
([ADR 0017](../adr/0017-project-access-scopes.md)): only permission holders who read
the Project find them (`404 agent_mail_draft_not_found` otherwise), and editing, deleting
or queueing them is posting in the chat, which needs `project.tasks.write` on
the Project (`403 project_permission_required`).

Draft groups are read for 1..100 Run ids with one comma-separated query value:

```
source_run_ids=01990ad8-0bb0-7de0-acfa-9f2821fc1a53,01990ad8-0bb0-7de0-acfa-9f2821fc1a54
```

The parameter is snake_case and is never repeated, matching the rest of the
HTTP query interface.

## Realtime

`mailbox.changed` is a PII-free refetch signal sent only to active members with
`mailbox.manage`. It carries a reason and, for a message change, the affected
`messageId`; email addresses and
content remain behind the authorized HTTP reads.

`mailbox.draft_changed` reaches only active permission holders who can read the
owning Conversation and carries only `{groupId, draftId, status, recipientCount, reason}`. A client
refetches the draft groups for that Conversation rather than accepting draft
content over the socket.

Mailbox Activity history and calendar counts use the same permission
boundary, including evidence stored before this restriction. Realtime audiences
are resolved by the producer, and are never widened to the whole Company.
Mutations recheck the acting membership's Mailbox permission under the canonical
Company and membership locks, so a stale principal cannot authorize a write
after losing the permission through a role change or membership revocation.
