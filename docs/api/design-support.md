The accepted desktop layouts use the existing company, agent, task, run and
conversation domains. This page maps each screen to its contract. The
per-domain OpenAPI files remain the detailed wire contract;
[overview.md](overview.md) describes how they are checked.

## Screen-to-contract map

| Desktop surface | Contract and behavior |
|---|---|
| Company switcher and company settings | [Companies](companies.md): accessible companies, current company identity, membership, and revisioned profile changes. Switching company changes the scope of subsequent requests. |
| Work: Board, Table, Focus and Dependencies | [Tasks](tasks.md): one canonical task projection, dependency edges, execution classification, assignment and task execution. These views do not create separate task stores. |
| Create task / delegate to agent | Task creation accepts a member or active Agent assignee. The assignee determines whether a Run can start; creating a task and starting execution remain explicit operations. A title-only task can be exported as part of a Company Plan. |
| Task properties | Task create/PATCH/read include `labels`, `startDate`, `dueDate`; attribution uses existing creator and creation time. Labels and dates are metadata and do not start runs or change task status. |
| Task detail, conversation and file preview | Task workspace and [Conversations](conversations.md) retain task/run context; attachments and saved results use existing authorized reads. Previewing a result does not mark the task done. |
| New private chat with an agent | `POST /conversations/direct` with a fresh `requestKey` creates an independent session with that agent. Reusing the key safely replays creation. The first user message supplies the title. |
| Pinned, Live Task and Recent | Direct/task conversation projections supply identity and title. `GET /conversations/pins` and conversation user-state GET/PATCH persist viewer-private pins. Live Task is derived from active task runs, pending Run-bound input and the `in_review` Task status, and is excluded from Recent. A task's pin does not mutate its shared conversation or task revision. |
| Agent roster, profile and instructions | [Agents](agents.md): canonical roster/detail, reporting relationships, runtime binding, instructions, model, thinking level and task capacity. Existing `agents.manage` rules remain in force. |
| Agent capabilities | Agent PATCH persists `capabilities`: disabled built-in groups, plugin bundles and MCP servers for the selected runtime. Settings are frozen at enqueue for new task/direct runs and enforced during daemon/provider preparation. |
| Computers & runtimes | [Runs and runtimes](runs.md): registration, availability, rename/removal and agent bindings. [Connector and Plugin catalogues](connectors-and-plugins.md) accept `runtime_id`, so a selected computer never displays a different runtime's discovery. Existing refresh and provider operations remain runtime-scoped. |
| Header Inbox preview and Inbox page | [Inbox](inbox.md) provides notifications and read state. [Approvals and questions](approvals.md) retain their own decision contracts; reading a notification is not an approval. |
| Team | Company membership and agent reporting relationships remain distinct. The UI can display both without inventing a grouping of its own. |
| My Account | [Authentication/account](authentication.md) provides the current user and profile mutation. Appearance remains a device preference, scoped locally to the user/company; there is no server-side appearance-sync API. |
| More: email, schedules, assets, memory | Existing [mailbox](mailbox.md), [schedule](schedules.md) and [workspace](workspaces.md) APIs. Provider connections, permissions, object storage and external service configuration are still prerequisites. |

All company routes above use `/api/v1/companies/{companyId}`. Abbreviated paths
in this table omit that prefix.

## New write semantics

- Task PATCH preserves omitted metadata. `labels: []` clears labels;
  `startDate: null` and `dueDate: null` clear their dates. Dates are calendar
  `YYYY-MM-DD` values, not timestamps. Labels are normalized and deduplicated;
  a start date after the resulting due date is rejected atomically.
- A new direct-chat `requestKey` belongs to one creator and company. It cannot
  be reused for another agent. Omitting it retains the existing quick-open
  behavior. Conversation ids are always generated by PostgreSQL.
- Task-chat personal state starts at revision zero. Pin writes use that
  independent revision and publish only to the acting user. Task chats cannot
  be archived through a personal-state request.
- Agent capability PATCH replaces the complete selection with all four fields:
  `runtimeId`, `disabledBuiltIns`, `disabledPlugins`, `disabledMcpServers`.
  Empty arrays inherit availability. Omission preserves the selection.
  Existing Agent revision and retry rules apply.

## Capability boundaries

Built-in Zenith Team skills control groups of `zenith-team-mcp` tools; the `wiki` group
controls the read-only Company Wiki tools (`wiki_search`, `wiki_list`, `wiki_read`) and, because
the daemon allowlist alone is not authority, the server's Run-proven Wiki read
routes for that Agent. Discovered Skills
are grouped by their containing plugin, so Skills and Plugins cards share one
bundle selection. Standalone native skill files are not independently
catalogued or switchable by this API.

A capability switch only restricts inherited capabilities. It cannot install a
plugin, authenticate a provider or grant Company Connector authority. MCP
execution still requires reviewed policy. Provider-native paths and credentials
remain on the daemon; PostgreSQL stores sanitized discovery and agent choices.

Queued runs and retry children retain their frozen settings. A runtime rebind
clears plugin/MCP ids from the previous runtime while preserving built-in
choices. Scheduled runs retain their separately reviewed exact Connector scope.
Native plugin restrictions apply only to the new provider process; shared
provider configuration is unchanged. If effective provider state cannot confirm
the restriction, the run fails. These controls do not replace a filesystem or
shell sandbox.

## Schema

The work-domain migration (`server/migrations/000004_work.up.sql`) creates task
metadata, direct-chat request keys and `conversation_user_states`. A fresh
database gets them by applying the full migration chain. The OpenAPI schemas
and the generated TypeScript client describe the same fields.
